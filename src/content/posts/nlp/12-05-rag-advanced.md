 **预检索（检索前）→ 检索 → 后检索（检索后）** 中常见的单点优化技术。

高级 RAG 的定义很薄：**在朴素 RAG 检索流程的前后各加一层优化**，流程本身不变。

```text
朴素：       建索引   ─────────→     检索     ──────────→    生成
高级：               [预检索优化] ─→  检索 ─→ [后检索优化]    → 生成
                 索引结构/查询方式        重排序/上下文压缩
```

| 朴素 RAG 的痛点 | 板块 | 对策技术 | 小节 |
| --- | --- | --- | --- |
| 嵌入无法表达"新旧"等非语义属性 | 预检索 | 元数据标注 | §2.1 |
| 检索单元大小两难 | 预检索 | 索引粒度、Small2big | §2.2 |
| 定长切块截断句子 | 预检索 | 滑动窗口、层次索引 | §2.3 |
| 大库检索算不动 | 检索 | ANN（KD-tree、LSH、HNSW） | §3.2 |
| 词面精确匹配丢失 | 检索 | 混合检索 | §3.1 |
| 召回含噪声与冗余 | 后检索 | 重排序 | §4.1 |
| 上下文过长分散注意力 | 后检索 | 上下文压缩（LLMLingua） | §4.2 |
| 用户问题问得不准 | 预检索 | 查询扩写/重写/路由 | §3.3（细节见 §5） |

## 预检索优化 ：给数据加结构

### 元数据标注

向量数据库大多支持向量与非向量的**元数据**共同存储。为文本块附加标识信息，检索时就能按结构化条件过滤，而不是纯靠嵌入相似度硬猜。

- 典型元数据：日期、章节/小节引用、小节标题、关键词；
- 教材例子：邮件查询应用中"越近的邮件越相关"——嵌入本身判断不出时间先后，把日期挂为元数据后，检索时优先取近期邮件；
- 作用：① 提高检索准确性（先过滤再算相似度）；② 给用户更精确的搜索体验。

元数据同时是**查询路由**的基础：元数据路由器先按元数据/关键词滤掉不相关块，再在剩下的块里检索（§3.3）。

### 索引粒度

索引粒度（检索粒度）= 检索单元的大小。由细到粗：

```text
Token → Phrase → Sentence → Proposition → Chunks → Document
```

两个方向的代价：

1. **粗粒度**：提供的信息多，但混入冗余与不相关内容，分散检索模型和下游 LLM 的注意力；
2. **细粒度**：语义完整性和知识覆盖度没保证，且检索单元数量暴增，检索系统负担大。

结论：按任务选粒度是性能杠杆，不是随手设定。工程上常用 **Proposition（原子事实句）** 和 **Chunk** 两档。

### 切块策略与层次索引

- **定长切块**：按固定词元数（128 / 256 / 512）硬切。问题：句子被截断到不同块，语义破碎；
- **滑动窗口**：块之间重叠，或用检索时合并多块的全局信息做分层检索，缓解截断；
- **Small2big**：折中方案——用**小粒度块做检索单元**（匹配准），命中后把**其前后的上下文一起召回**（喂给 LLM 的内容完整）。检索和读取用两种粒度；
- **层次/树状索引**：给文档建父子结构，**摘要挂在父节点**上。检索先在粗的父层（摘要）定位，再下钻子块，显著提高效率；这也是 LongRAG 类"摘要节点 + 细节节点"双层的雏形。

## 检索阶段的技术

### 编码方法：稀疏 vs 稠密

BM25 与余弦相似度公式，这里补"为什么必须走向稠密、又为什么要保留稀疏"：

1. **稀疏编码**（One-Hot、词袋、TF-IDF、BM25）：反映词频信息，但两个病根——
   - **语义鸿沟**：词与词之间算不出相似度（同义改写直接漏检）；
   - **维度爆炸**：稀疏向量维度与词典等长，存储和计算都浪费；
2. **稠密编码**：编码器把文本压成低维稠密向量，大模型训练过的编码器能充分反映语义，查询-文档相似度计算准确得多；
3. **混合检索**：两者捕获的特征互补，加权融合分数——
   - 稀疏模型先做初步检索，**大幅缩小搜索范围**；
   - 研究表明稀疏检索能**增强稠密模型的零样本检索能力**，并协助处理**包含稀有实体的查询**（罕见专有名词嵌入学不好，词面匹配能兜底）。

### 近似最近邻（ANN）搜索

精确最近邻在真实库里不可行，原因有二：

- 高维向量规模庞大，逐一算相似度计算成本极高甚至不可行；
- LLM 系统不是确定性系统，检索追求的是**语义上"足够接近"**，不是绝对最优解——类比推荐系统，用户不关心每个推荐是不是全局最佳匹配。

代表方法按索引结构分：

| 路线 | 代表 | 思路 |
| --- | --- | --- |
| 树 | KD-tree | 低维友好，高维退化 |
| 哈希 | LSH 局部敏感哈希 | 相似向量大概率撞进同一桶 |
| 图 | HNSW | 多层可导航小世界图，RAG 默认常客 |
| 聚类 | IVF（常配 PQ） | 先分簇再簇内搜索 |

量化（PQ/OPQ/AQ）与 IVF/HNSW/Graph/LSH 的组合细节见 [推理框架与部署](/posts/nlp/11-01-inference-frameworks/) 的向量索引部分，此处不重复。

### 查询优化

预检索的另一半是优化**查询**——用户很难提出精确清晰的问题，拿原始查询硬检是朴素 RAG 的主要失分点：

- **查询扩写**：单查询 → 多个相关查询；
  - 多查询（multi-query）：LLM 直接把原查询扩成多个语义相关的变体；
  - 子查询（sub-query）：把复杂问题**分解**为一系列子问题分别检索；
  - 扩展出的查询需 LLM 验证可靠性，即**验证链（Chain-of-Verification, CoVe）**；
- **查询重写**：原查询 → 一个更适配检索的新查询（替换而非增广）；
  - 提示词驱动：直接让 LLM 转写；
  - 专职小模型：**RRR**（Rewrite-Retrieve-Read）、**BEQUE**——不占用主模型，延迟低；
- **查询路由**：把不同查询导向最相关的索引区域（对应模块化 RAG 的路由模块）；
  - 代表：**元数据路由器**——从原始数据提取关键字 → 按关键字滤掉不相关块 → 只在相关块中检索。

## 后检索优化

召回 ≠ 可用。进入提示词之前还有两道工序。

### 重排序（rerank）

- 动机一：召回的 Top-K 里仍有不相关块，用重排模型（如 cross-encoder）对候选**重新打分排序并截断**，粗排召回、精排筛选的两阶段结构；
- 动机二：**信息摆放位置**。LLM 与人类阅读类似，主要关注文本**开头和结尾**、忽略中间（"中间丢失"，lost in the middle）——所以重排序模块会把**重要块放到最终提示的头或尾**；

### 上下文压缩

过长的上下文 ① 分散生成模型的注意力 ② 拖慢推理。压缩的目标是**只保留对回答有用的关键信息**。

代表：**LLMLingua**，两级漏斗

1. 对提示中的 few-shot **示例排序**，按比例**删掉不重要的示例**；
2. 对留下的示例，用同样的思路**删掉不重要的词元**（token 级压缩）。

效果：提示显著变短，关键信息密度上升。
