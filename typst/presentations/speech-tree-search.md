# Agentic Tree Search 原理详解

## 一、为什么需要树搜索？

v1 的实验范式是线性的。它的工作方式是：

> Aider 编辑 experiment.py → 运行 → 如果失败，重试最多 4 次 → 收集结果 → 进入下一轮，最多 5 轮 → 结束。

这个过程的本质是**一条链**。想象你在走迷宫，每次只选一条路走到底，遇到死胡同就退一步再试一次。如果 4 次都失败，这条路就放弃了。问题在于：

1. **你永远不知道其他路会不会更好**——因为你根本没试过其他方向
2. **实验深度有限**——5 轮很快就用完了，无法做细致的消融或调参
3. **错误的代价很高**——如果早期决策有误（比如选了错误的学习率、错误的模型架构），整个链都会偏掉

在真实的科研中，好的科学家不会只沿着一条路走到黑。他们会同时探索几个方向，快速排除不靠谱的，在最有希望的方向上持续深入。v2 的树搜索就是模拟这个过程。

## 二、树搜索的核心思想

v2 的核心变化可以概括为一句话：

> **不是一条路走到底，而是种下一棵树，让它分叉生长，择优传播。**

具体来说，v2 的每个实验不再是一个单链，而是一棵树。树上的**每个节点**代表一个完整的实验尝试，它包含以下信息：

```
一个节点 = {
  实验代码 (Python 脚本)
  实验计划 (高层的文字描述)
  执行错误 (如果有)
  运行时间
  指标结果 (loss, accuracy 等数值)
  LLM 对这个代码的反馈
  绘图脚本和生成的图片文件
  VLM 对图片的反馈
  节点状态: "buggy" 或 "non-buggy"
}
```

每个节点都要经历一个完整的**执行循环**：

> **Plan → Code → Execute → Plot → VLM Review → 分类**

这个过程是：

1. LLM 先生成一个实验计划——它要做什么、改什么
2. 然后生成对应的 Python 代码
3. 立即执行这个代码
4. 如果执行成功，调用 plot 脚本可视化结果
5. 把生成的图片交给 VLM（GPT-4o）审查
6. 根据结果把节点标记为 buggy 或 non-buggy

**这里的关键是 VLM 审图**。v1 完全不知道图长什么样，v2 的 VLM 会检查：

- 图的坐标轴标注是否清晰？
- 图例是否缺失？
- 图表和论文描述是否对齐？
- 有没有有意义的结论？

如果有问题，这个节点就被标记为 buggy，进入修复流程。

## 三、搜索策略：Buggy 与 Non-buggy 的博弈（约 3 分钟）

这是树搜索最核心的设计。每次要扩展新节点时，系统需要决定：**在哪个节点上生长出子节点？**

策略非常简单但有效：

> 以固定概率选择 Buggy 节点或 Non-buggy 节点。

- 如果选中了 **Buggy 节点**：创建 Debug 子节点，带上错误信息让 LLM 修复。Debug 最多嵌套 3 层——如果 3 次都修不好，这个分支就放弃。
- 如果选中了 **Non-buggy 节点**：创建 Refine 子节点，让 LLM 在已有基础上改进实验（比如换更大的模型、加更多数据、试不同的设置）。

当在多个 Non-buggy 节点中选择时，系统使用 **Best-First 搜索策略**：

- 让 LLM 评估每个 Non-buggy 节点
- 评估依据包括：性能指标、训练曲线收敛情况、生成图表的质量
- 选最好的那个去扩展

这个设计的好处是：

- **Buggy 节点不会一直被忽略**——即使代码有 bug，系统也会优先尝试修复
- **Non-buggy 节点会持续改进**——好的代码会被进一步优化
- **并行扩展**——每次选中多个节点同时生成子节点，然后一起执行

## 四、四种特殊节点类型（约 2 分钟）

除了基础的 Buggy/Non-buggy，v2 引入了四种特殊节点，对应不同类型的实验需求：

**1. Hyperparameter 节点（Stage 2）**

- 专门用于超参数搜索
- 系统会记录已经测试过的超参数配置，避免重复实验
- 如果某个超参数实验报错，同样会创建 Debug 节点去修复

**2. Ablation 节点（Stage 4）**

- 专门用于消融实验
- 同样会追踪已测试的消融条件，防止重复
- 评估某个组件到底有没有用

**3. Replication 节点（Stage 3-4）**

- 用不同的随机种子重复父节点的实验
- 目的是获取统计量（均值和标准差）
- 一般会创建多个复制节点

**4. Aggregation 节点（Stage 4）**

- 这类节点**不执行任何实验**
- 它的唯一工作是：读取所有复制节点的结果，生成汇总图表
- 这是最终论文中带有 error bar 的那些图的来源

## 五、四阶段进度管理（约 2 分钟）

光有树搜索还不够，还需要有人管理整个研究进度。这就是 **Experiment Manager** 的角色。它把整个实验过程划分为 4 个阶段，每个阶段有明确的目标和终止条件：

### Stage 1: 预研（21 个节点）

- 输入：Idea 描述
- 目标：快速验证想法是否可行
- 从零开始生成代码，建立最小可行原型
- 21 个节点并行探索不同的实现方式
- 终止条件：**有一个原型能成功执行**

关键决策：这个阶段不追求性能，只追求"能跑起来"。LLM 被明确要求"先写一个简单但能工作的版本"。

### Stage 2: 调参（12 个节点）

- 输入：Stage 1 选出的最佳原型
- 目标：优化关键超参数（学习率、epoch 数等）
- 超参数节点搜索最佳配置
- 终止条件：**训练曲线收敛，且至少在 2 个数据集上验证通过**

### Stage 3: 议程执行（12 个节点）

- 输入：调优后的基线
- 目标：实现核心研究议程，验证假设
- Refine 改进 + Debug 修复持续进行
- 有一个独特的设计：**如果实验完成时间远短于分配的时间预算**，系统会自动建议增加实验复杂度
- 终止条件：**计算预算耗尽**

### Stage 4: 消融（12 个节点）

- 目标：系统评估各个组件的贡献
- 消融节点 + 复制节点（多 seeds）+ 聚合节点
- Aggregation 节点最终生成带有统计信息的论文图表

### 阶段间传播

每个阶段结束时，LLM 评估器会从当前阶段的所有 Non-buggy 节点中**选出最佳的一个**，作为下一阶段的根节点。这个选择基于：

- 性能指标（loss、accuracy 等）
- 训练动态（曲线是否稳定收敛）
- 图表质量（VLM 评分）

## 六、与 v1 的关键差异总结（约 1 分钟）

| 维度       | v1 线性               | v2 树搜索              |
| ---------- | --------------------- | ---------------------- |
| 探索方式   | 单链，一条路走到黑    | 并行多路，择优深入     |
| 错误处理   | 重试 ≤ 4 次，失败放弃 | Debug 子树，最多 3 层  |
| 实验多样性 | 低（只有一条路径）    | 高（多分支并行）       |
| 图表验证   | 无                    | VLM 自动审查           |
| 资源利用   | 串行执行              | 并行节点，充分利用算力 |
| 可复现性   | 每次运行不可控        | 复制节点提供统计量     |
| 单篇耗时   | 1-2 小时              | 数小时 ~ 15 小时       |

## 七、关键技术参数（快速参考）

```
代码生成模型:     Claude 3.5 Sonnet (v2), T=0.5
VLM 反馈模型:     GPT-4o, T=0.5
最大 Debug 深度:  3 层
单节点超时:       1 小时
Stage 1 节点数:   21
Stage 2-4 节点数: 12
总耗时:           数小时 ~ 15 小时
```

## 八、一个具体的例子（如果需要的话）

假设我们的 Idea 是："给 LSTM 加一个正则化项，让相邻时间步的 embedding 更接近，看看能不能提升组合泛化能力。"

Stage 1 会并行生成 21 种不同的代码实现——有人用 L1 正则，有人用 L2 正则，有人用 cosine distance，有人用 MSE。全部执行后，只有那些能成功跑出结果的被标记为 Non-buggy。LLM 评估器选出效果最好的那个。

Stage 2 对这个最佳实现做调参：学习率 1e-3 还是 1e-4？正则化强度 0.01 还是 0.1？同样并行搜索。

Stage 3 基于调好的参数，执行核心研究议程：在简单任务和复杂任务上分别测试，看正则化是否真有帮助。

Stage 4 做消融：不用正则化会怎样？用正则化但去掉 LSTM 会怎样？在 Transformer 上效果一样吗？

最终，复制节点跑 5 个不同的随机种子，聚合节点生成带 error bar 的论文图表。

这就是整个过程：**从一片代码的森林开始，快速砍掉不行的树，在最粗壮的树上持续生长，最后结出论文的果实。**
